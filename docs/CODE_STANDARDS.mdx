# Refreeg code standards

Short rules, each one earned from a real review correction. Follow them for new code and for any file you substantially change. Do not mass-rewrite old files; fix them when you next touch them.

Visual rules (colors, typography, shared UI) live in [DESIGN_GUIDE.md](./DESIGN_GUIDE.md). This page covers structure and code.

## Where code lives

| Layer            | Location                                | Job                                                                                  |
| ---------------- | --------------------------------------- | ------------------------------------------------------------------------------------ |
| Server actions   | `actions/<domain>/<feature>-actions.ts` | Auth check, input check, one Prisma or provider call, return a result. Nothing else. |
| Provider clients | `services/`, `lib/`                     | Talk to Paystack, Flutterwave, Breet, mail. No UI knowledge.                         |
| Hooks            | `hooks/use-<feature>.ts`                | React Query wiring and any post-processing of a result.                              |
| Schemas          | `lib/schemas/<feature>.schema.ts`       | One zod schema per form.                                                             |
| Options          | `lib/options/<feature>.options.ts`      | Label and value lists.                                                               |
| Types            | `types/<feature>-types.ts`              | Shared types and interfaces. Never declared or exported from `actions/`.             |
| Components       | `components/<domain>/<Component>.tsx`   | Thin. Render, call hooks, hold local UI state.                                       |

Domain folders keep the flat namespaces small:

- `actions/`: `admin/`, `causes/`, `petitions/`, `donations/`, `users/`. The `index.ts` barrel stays at the root.
- `components/`: `layout/`, `causes/`, `engagement/`, `profile/`, `marketing/`, plus the existing feature folders (`home/`, `discover/`, `auth/`, `dashboard/`, `docs/`, `saved/`, `creators/`, `fees/`, `giving/`, `healthcare/`, `app-shell/`) and `ui/` for shadcn primitives.
- `lib/`: `api/`, `causes/`, `payments/`, `rewards/`, `saved/`, `referrals/`, `schemas/`, `options/`, `s3/`, `media/`, `auth/`, `health/`. Shared singletons stay at the `lib/` root (`prisma.ts`, `utils.ts`, `event-bus.ts`, and similar). `lib/public-file-manifest.ts` is generated; never move it or hand-edit it.
- `scripts/`: `db/` (one-off data fixes), `ops/` (manual maintenance jobs), `one-off/` (test and dev scratch scripts). Deployment and cron-facing files referenced by CI or the servers (`remote-deploy*.sh`, `rollback*.sh`, `bootstrap-instance.sh`, `send-recovery-emails.ts`, `backup-db.sh`, `setup-db-backup-cron.sh`, `sync-s3.ts`) stay at the `scripts/` root because workflows and crons call them by path.

## File naming

Component files are `PascalCase.tsx` (`components/layout/Header.tsx`, `components/causes/DonateButton.tsx`). Hook, lib, util and action files stay lowercase (`use-cause-form.ts`, `cause-actions.ts`). Files in `components/ui/` keep their lowercase shadcn names; do not rename them. Do not bulk-rename untouched files: apply the rule when a file is moved or substantially changed.

Older `*-constants.ts` files stay until a change touches them.

## 1. Actions only do the work, nothing around it

An action authenticates, validates, performs one operation and returns `{ success, error }` or the data. It does not format for display, open anything, or toast. Parsing, renaming, building view objects and side effects go in a hook.

```ts
// actions/users/referral-actions.ts: the request only
export async function getReferralDashboard() {
  const session = await auth();
  if (!session?.user?.id) return { success: false, error: "Not authenticated" };
  return { success: true, data: await loadDashboard(session.user.id) };
}

// hooks/use-referrals.ts: post-processing lives here
export function useReferralDashboard() {
  const query = useQuery({
    queryKey: ["referrals"],
    queryFn: getReferralDashboard,
  });
  return {
    dashboard: query.data?.data ?? null,
    error: query.data?.error ?? query.error?.message ?? null,
  };
}
```

## 2. No intermediary layers

Make the plain call. Use the backend's own pagination and filters. Do not add a wrapper hook that fetches every page and merges, a mapper that renames fields for no reason, or a helper used once.

Before adding a hook, helper or abstraction ask: does the existing query plus a filter or a page state already solve it? If yes, stop.

This does not forbid a hook that holds post-processing a reviewer asked for (rule 1). It forbids wrappers that re-fetch, re-merge or re-shape for no reader.

## 3. Show the real error, no error maps

Errors shown to people come straight from the action result or the query: `result.error`, `query.error?.message`. Do not add an error helper, a `*_ERRORS` constant, per-status wording, or generic "Something went wrong" strings at call sites.

Field-level validation errors (rule 5) are separate and stay.

If the server message is not fit to show, fix the message in the action. Do not translate it in the component.

## 4. One state object per form

Applies to forms and dialogs with related fields. Tab, open and loading flags in non-form components stay separate `useState` calls.

Related fields share one `useState` object and one updater named `setFormFields`. No `useState` per field.

```tsx
const [form, setForm] = useState({
  name: item?.name ?? "",
  description: item?.description ?? "",
});
const setFormFields = <K extends keyof typeof form>(
  key: K,
  value: (typeof form)[K],
) => setForm((current) => ({ ...current, [key]: value }));

<Input
  value={form.name}
  onChange={(event) => setFormFields("name", event.target.value)}
/>;
```

When one change must set two fields, call `setForm` directly in that handler. Two forms that share fields and submit flow (the pledge page and the Discover pledge dialog) share one hook, such as `hooks/use-pledge-form.ts`, instead of copying the state.

## 5. Validate with a zod schema

Every form has a schema in `lib/schemas/<feature>.schema.ts`, checked with `useValidator({ store: form, schema })` from `hooks/use-validator.ts`. It returns `errors`, `validate()` and `clearError(key)`; show `errors.<field>` under each input. The schema checks presence, format and relations between fields, such as end date not before start date.

```ts
const { errors, validate, clearError } = useValidator({
  store: form,
  schema: pledgeSchema,
});
if (!validate()) return;
```

Do not repeat limits the server owns (fee caps, provider minimums, rate limits). Those come back as errors from the action and show through rule 3.

Keep the submit order: validate, then guard against double submit, then call the action. Forms already built on React Hook Form keep it with `zodResolver`; do not mix both in one form.

## 6. One dialog per file

Each dialog (create, edit, delete, confirm) gets its own file named for what it does, such as `create-pledge-dialog.tsx`, exported by name with its own imports. The page or section file only imports dialogs and decides which is open. Share constants through a helper, never by copy.

Use the existing `AlertDialog` (`components/ui/alert-dialog.tsx`) or `Dialog` for plain confirm and delete cases before building a custom modal.

## 7. Option lists go in options files

Every `{ label, value }` list lives in `lib/options/<feature>.options.ts`, typed once and named `xxxOptions`.

```ts
// lib/options/pledge.options.ts
import type { Option } from "@/types/options";

export const pledgeFrequencyOptions = [
  { label: "Weekly", value: "weekly" },
  { label: "Monthly", value: "monthly" },
] as const satisfies readonly Option[];
```

Not `UPPER_CASE`, and not inside a component, helper or constants file. Components that accept `options` props take a `readonly` array.

## 8. Say it once

When the same expression, lookup or type-based branch appears twice in a file, compute it once: a variable, or a small helper or hook in that file. Scan the files you wrote for repeats before you finish.

## 9. Use what exists

Before writing raw HTML, check `components/ui/` and the shared components. Look for existing pieces first: `EmptyState`, `CalloutBanner`, `Eyebrow`, `Card`, `Button`, `Badge`, `AlertDialog`.

- Empty list: render the one list component and vary its empty message by state. Do not wrap it in a ternary with a second empty component.
- Banner, status chip, stepper: use the shared component, not a one-off.
- Typography: use shared typography from `@/components/marketing/Typography` (`Heading`, `P`, `Lead`, `Small`, `Strong`, `Span`) instead of raw typography HTML elements (`h1`–`h6`, `p`, `span`, `small`, `strong`).
- Colors and fonts: tokens from the design guide, never hardcoded values.

## 10. Small and flat

- One component per file. A component over about 200 lines is a candidate to split.
- Early returns over nesting.
- No dead code, commented-out blocks or unused exports left behind.
- Names say what a thing is. Plain words over clever ones.
- Add a comment only when the reason is not obvious from the code. Say why, not what.

## 11. Tables use the shared DataTable

Every table renders through `components/ui/data-table.tsx` (shadcn base data-table on TanStack Table v9): a `columns.tsx` built with `createColumnHelper`, the shared `data-table-features.ts`, and `<DataTable columns data />`. Client-side pagination state lives in the page or client that owns the filters. Do not hand-roll `<Table>` markup inside a card; the shell owns header styling, row borders and the pagination footer (`data-table-pagination.tsx`).

```tsx
const columns = useMemo(() => kycQueueColumns(tab), [tab]);
<DataTable
  columns={columns}
  data={filtered}
  pageSize={8}
  pageIndex={pageIndex}
  onPageIndexChange={setPageIndex}
  pagination
/>;
```

## 12. Dialog and form submits run through useMutation

A dialog that calls a server action wraps the call in `useMutation` from `@tanstack/react-query`, validates with `useValidator` first (rule 5), guards against double submit with `isPending`, and handles the result in `onSuccess`: show `result.error` via `FieldError` (rule 3) and return early; otherwise close and navigate. No hand-rolled `isSubmitting`/`submitError` state around a plain async handler.

## 13. Types live in `types/`, never in actions

Actions files export async functions only. Any type or interface a server action returns or accepts (result shapes, row types, input types) goes in `types/<feature>-types.ts` and is imported with `import type` by the action, the hook and the component. A `"use server"` file must not be the source of a type other layers import.

```ts
// types/admin-overview-types.ts
export type AdminOverviewData = { role: "admin" | "manager" /* ... */ };

// actions/admin/admin-overview-actions.ts
import type { AdminOverviewData } from "@/types/admin-overview-types";
export async function getAdminOverview() {
  /* ... */
}

// hooks/use-admin-overview.ts
import type { AdminOverviewData } from "@/types/admin-overview-types";
```

## 14. Admin screens inherit the shell and WorkspaceFrame

Never inject arbitrary layout wrappers (e.g. `ClientLayoutWrapper` with radial gradients or glassmorphic overlays) into dashboard routes. Every `/dashboard/admin/*` screen inherits chrome from `AdminShell` (`bg-cream`) and page padding from `<WorkspaceFrame>` (`components/admin/workspace/workspace-frame.tsx`, `px-4 py-8 sm:px-8 max-w-[1440px]`). Never add redundant server-side role checks (`if (role !== "admin")`) inside `/dashboard/admin/*` page components — `middleware.ts` already guards `/dashboard/admin/*` routes globally. Actions and overview queries must access recently migrated or optional models defensively (e.g. `(prisma as any).<model>?.aggregate`) with fallback defaults so schema evolution never crashes the overview.
## 15. Prisma: typed client first, safe schema and migrations

- Use the typed client for CRUD. Reach for `$queryRaw` only for window functions, `percentile_cont`, CTEs or `DISTINCT ON` the client cannot express (rule 15).
- Select only the columns used (`select`), never whole rows. Batch with `findMany({ where: { id: { in } } })` or `groupBy`, never a query inside a loop.
- Writes that must succeed together use `$transaction`. Do the guard read inside it, or make the write conditional (`updateMany({ where: { id, status: { not: "removed" } } })` and check `count`), so two callers cannot both pass a stale check.
- Use `create` and catch `P2002` for unique conflicts. `createMany` is for real batches only.
- Handle `P2025` (not found) and return `{ success: false, error }`. Log the Prisma error server-side; return a stable message, never raw Prisma or SQL text.
- Every model declares its relations (`@relation` with an explicit `onDelete`), real enums or a CHECK for closed value sets, `@db.Timestamptz(6)` for times, `@db.Decimal` for money, and an index for every column used in a `where`, `orderBy` or join. Composite index order matches the filter (equality columns first, range column last).
- One migration per change, generated by `prisma migrate dev`. No hand-written `IF NOT EXISTS` to hide drift; repair a bad history with `prisma migrate resolve`. Never create the same table in two migrations. Every model the code uses exists in `prisma/schema/`.
- Never edit an applied migration. Add a new one. Avoid long locks: add indexes `CONCURRENTLY` on large tables, add columns nullable first, backfill in batches.

## 16. SQL: parameterized, bounded and indexed

- Parameters only. Interpolate values with the `Prisma.sql` template. `Prisma.raw` is allowed only for a literal union of identifiers, never user input. Do not splice constants into strings (`interval '${n} hours'`); use `make_interval(hours => ${n})`. Cast bound params where the type is ambiguous (`${n}::float8`, `NULL::text`).
- Bound every scan: filter by date or id list before joining, never scan a whole table for a per-row answer. Pass `= ANY(${ids}::uuid[])`, not a concatenated `IN`.
- No self-joins on large unindexed or computed columns (images, long text). Store and index a hash instead.
- No correlated subquery per row; use a CTE, `FILTER` or a join. No unbounded window over all history.
- Joins that can fan out (audit rows, multiple reviews) are deduped first (`DISTINCT ON (id) ... ORDER BY created_at`), then counted. Do not mix `COUNT(*)` and `COUNT(DISTINCT id)` over the same join.
- Name columns, never `SELECT *`. Qualify columns in joins. Use `COALESCE` and `NULLIF` for null and divide-by-zero. Use `TIMESTAMPTZ`, compare half-open ranges (`>= from AND < to`).
- Heavy reports are cached (`unstable_cache` with a tag) and invalidated with `revalidateTag`. Check the plan with `EXPLAIN (ANALYZE, BUFFERS)` on realistic data before adding a new report query.
- Raw SQL result types live in `types/` (rule 13). Convert `bigint`, `numeric` and `Decimal` results to `number` once, at the edge.

## 16. Server actions are public endpoints

A `"use server"` export can be called by anyone with the URL, so it must stand on its own.

- Every action that reads or writes protected data authenticates and authorizes itself (`requireAdminOrManager()` and similar), including read-only report actions. A layout or page gate is not enough.
- Never trust identity or request data passed as an argument (`userId`, `userAgent`, role). Read it from the session or headers inside the action.
- Internal helpers that must not be callable from a client are not exported from a `"use server"` file. Put them in `lib/` or `services/`.
- Anonymous write endpoints (tracking, webhooks) go through a route handler with rate limiting and input validation, not a bare action.

## Review procedure

When asked to review or rate changes against the standard:

1. List changed and untracked files.
2. Check each file against rules 1 to 16 and `DESIGN_GUIDE.md`.
3. Report violations as `file:line`, the rule number, and the fix.
4. Fix them when asked, then review again until clean. Also run `pnpm lint` and `pnpm tsc --noEmit`.

## Recording corrections

When a reviewer or the team corrects a pattern, add it here as a rule with a short example, and mirror it in `.agents/skills/refreeg-code-standards/SKILL.md` and `AGENTS.md`. One source of truth for the reason; the skill holds the checklist.
